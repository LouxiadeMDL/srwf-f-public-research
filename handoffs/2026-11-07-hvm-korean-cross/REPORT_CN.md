## 2. EB.01：有序当前对象对，而不是说得次数

原版F主表EB指向`0x0601E3C4`，EB.01子处理器为`0x0601E438`。它两次调用原helper`0x06026EE4`获得选择器对应的actor集合，依次比较全局`0x060C0694`和`0x060C0695`。两边成功才清除条件字节`0x060C0715`的bit7，共享数值`0x060C0704`不更新，返回`0x6005`。

可读规则：**当前第一对象属于选择器A集合，且当前第二对象属于选择器B集合。顺序有意义。**

| 原版场景内位置 | 参数A / B | F0成立目标 | 后续Flag查询 |
|---|---|---|---|
| P12 +0C0B | 007E / 0084 | 0C21 | 00E2 |
| P12 +0C15 | 0084 / 007E | 0C21 | 00E2 |
| P30 +09AE | 0025 / 0017 | 09C4 | 00E1 |
| P30 +09B8 | 0025 / 0016 | 09F9 | 00E2 |
| P47 +0855 | 0025 / 0017 | 086B | 00E1 |
| P47 +085F | 0025 / 0016 | 08A0 | 00E2 |

合成机师007E关联actor3、0084关联actor5。原函数验证：当前对(3,5)匹配007E/0084；只交换当前对失败；同时交换当前对及参数又成功。另测两边同对象，共六例，无游戏callee替代。GS人物/机体区及累计没有被改写。

因此P12的反向两条条件是允许两个方向落入同一后续块，不是累计两次说得。P30/P47按不同第二对象分流。解释器应将root11对象对与root9说得资格、D0存储状态分域。

**尚未确定：** 两个当前对象全局的自然生产者及所有调用用途，不能全局命名为攻击者/防御者；负选择器、别名/同乘链、完整root11自然剧情也不由这六例证明。场景SHA与结构字段见[ROOT11_PAIRS.json](ROOT11_PAIRS.json)。

## 3. C2.0E：库存局部字段接上原增物函数

上游指令文档区分C2.0E单个部件增加、C2.11重复增加。本轮在原版F执行`0x0602BB80`的C2.0E，而不是直接把上游说明当作原版结果。[S01]

地址为`GS+0x574+index`，有效编号0至29，原值0至8增加1，9或更大值不再增加。有效写入PC为`0x0602BBB2`。

| 参数 / 原值 | 实际结果 |
|---|---|
| index10 / 0 | GS+057E由0变1 |
| index10 / 8 | 8变9 |
| index10 / 9 | 保持9，不写 |
| index10 / 255 | 保持255，不自动修复 |
| index29 / 0 | GS+0591由0变1 |
| index30 / 0 | 越界，不写 |

第18话曾局部校准的`GS+057E`和已提取保存载荷`+DE`，因此能接到原函数的index10；它不是隐藏累计字段。第21话同时发生的累计6→7与库存字节0→1，应分别追D0加点路径及index10的掉落/增物路径。

原版P17未找到直接对应index10的C2.0E/C2.11原字形态，不能据此断言无奖励；也可能经敌机掉落参数和通用结算。此处只确认计数字段及原操作，不证明含已装备零件的总持有量，也不自动认证VB7/VB8全部库存语义。

## 4. C1.0A：存在性谓词与气力数值必须分开

上游防重文档讨论机师缓存存在守卫，指令文档则说明C1.0A读取机师气力；应以返回数值和成功谓词结合理解，不能只看名称。[S01/S02]

本轮执行原F`0x06028894`：存在的007E、0084返回合成气力100并清失败位；不存在的01EE设置失败位，但保留旧共享数值`0x77777777`。三例均未创建人物或修改低RAM对象数据。

所以“返回数值大于0即已在队”的判断不成立。接口必须区分found与value，说明查询的是人物缓存、关联机体还是战场actor。

雷西在说得前已有机师缓存。若直接套用为新建人物设计的“ID存在就完成”，会在尚为敌方时错误跳过事件。应结合已验证的关联、加入模式、归属和阶段。此结论不表示C1.0A与上游FF C0.11是同一用途。

## 5. root5与root8的防重复机制不能通用

上游原生增援研究记录：root5的pending/done恢复位置可保存在GS+0528，通过游戏内保存和新进程Continue后仍进入done路径、不重复创建，并保留原5/6回合事件。初版新增人物ID与原事件目标冲突，换ID后才完成该限定检查。原始游戏证据未公开，本轮只审读文档，不重报为自己的游戏运行。[S04]

root8文档则说明：原包装每次重选root8起点，写入+052C再调用，单独划出pending/done代码并不能阻止下一次从头运行。[S03]

应用于P09：复用已恢复的原提交包装，但先核对宿主怎样进入/恢复；不要任意占用未知Flag、删掉原胜负流程，或假定任意root的恢复PC都能保证一次性。角色已经存在也不等于已加入，这两项必须一并测试。

## 6. 地址对齐：旧限定执行器的一项盲区

上游11月6日修复记录指出，部分名称指针单元地址为2 mod 4，旧版用mov.l造成SH-2地址错误，新版改用两个word访问并增加对齐检查。该提交还同步新增机体重打包后的六个能力画面资源表项。[S06及修复提交]

本轮检查的是2026-10-18归档执行器，不泛指全部后继版本。旧Memory实现按字节切片，没有word/long对齐检查。执行自写合成的长字读取：地址20000002时旧执行器返回02030405，新增StrictMemory拒绝；对齐地址两者均成功。四个探针符合预期。

这是候选SH-2补丁测试的盲区，不推翻已有自然游戏证据。StrictMemory只拒绝非法访问，不实现真实异常向量，也不是完整硬件认证。CrossCPU仅补三种所需CPU操作，不hook游戏callee。

资源修复则提示：重打包C_ROBOT后，只更新TSR root1表头副本可能遗漏其他引用；上游FF要求同步decoded TSR+6BA98的六个8字节单元并绑定EXEC来源。此地址只属于其版本，是资源引用审计线索，不是中文镜像故障已经定位。

## 7. 对工具实现的直接用途

1. 把EB.01落实为有序当前对象对条件，追两个当前对象值的生产者，不与说得次数合并。
2. 将index10增物函数用于库存生产者追踪，把第21话累计与奖励分别解释。
3. P09 Auto继续复用原提交服务；加入宿主恢复方式、原目标已存在、等待重入等反例。
4. 候选原生代码必须通过对齐检查；F/FF指令长度也分别绑定，不能只因opcode同名共用长度表。

这些是接入方向，不代表Auto候选已经发布。已经验证的手动说得、兜底和冷读基线仍保留，不要求反复重打。
